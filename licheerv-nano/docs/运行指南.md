# 从零配置与重启后的运行

## 1. 先准备什么

- LicheeRV Nano SG2002、匹配排线的 GC4653 摄像头、TF 卡及稳定供电。
- 使用匹配板卡和摄像头的厂商 Buildroot 镜像。当前已测环境为 Buildroot 2023.11.2 / RISC-V；原始镜像文件名和校验值未记录，任意其他镜像不保证兼容。
- 板卡必须有 Python 3、`/mnt/system/usr/bin/sample_venc` 与配套多媒体库。
- Windows 或 Ubuntu 电脑需要 Python 3、OpenSSH、FFmpeg；现有实测为 Windows + FFmpeg 7.1。Ubuntu 运行尚待验证。
- 板卡不是 Ubuntu；不要在 Buildroot 上执行 apt 或照搬 systemctl。

参考：[板卡外设教程](https://wiki.sipeed.com/hardware/zh/lichee/RV_Nano/5_peripheral.html)。关电安装摄像头，核对排线方向。不要刷 reCamera 固件替代本板系统。

## 2. 连接 SSH 和可选 Wi-Fi

USB 网卡安装/枚举完成后，本项目默认使用板卡 `10.225.161.1`：

```sh
ssh root@10.225.161.1
```

密码按实际系统设置输入；首次连接核对主机指纹。发布包不记录现场密码。Wi-Fi 非必需，USB 可完成部署和视频接收。

本次镜像曾通过 `/boot/wifi.ssid` 和 `/boot/wifi.pass` 保存 Wi-Fi 配置；如需修改，先核对镜像启动脚本是否读取这两个文件，再用板端编辑器填入自己的配置，不把文件提交到仓库。查询连接情况：

```sh
ip -4 addr show wlan0
```

Wi-Fi 地址由 DHCP 分配，重启后可能变化；不把旧现场地址当作固定 IP。

## 3. 首次部署板卡脚本

SSH 中先执行：

```sh
mkdir -p /mnt/data/codex-h264-sender
```

电脑从仓库根目录上传：

```sh
scp licheerv-nano/scripts/h264_sender.py root@10.225.161.1:/mnt/data/codex-h264-sender/h264_sender.py
```

这个文件存储在板卡 `/mnt/data`，重新上电不需要再次上传。`/tmp`、`/run` 的管道和 PID 则会失效。

## 4. 板卡重新上电后启动

登录 SSH，先检查没有其他摄像头程序或重复发送器：

```sh
ps | grep -E 'h264_sender|h264_preview|sample_venc|sample_vio|sensor_test|camera_preview|ffmpeg'
```

若已有发送器和编码器，不重复启动。确认摄像头和端口 9000 空闲后：

```sh
export LD_LIBRARY_PATH=/mnt/system/usr/lib:/mnt/system/lib
nohup python3 /mnt/data/codex-h264-sender/h264_sender.py > /tmp/h264-sender.log 2>&1 < /dev/null &
cat /run/h264-sender.ready
tail -n 30 /tmp/h264-sender.log
tail -n 30 /tmp/h264-sender-encoder.log
```

正常模式会创建 FIFO 并启动硬件编码器，SSH 退出后继续运行。不要复制迁移时的 `--adopt-pid` 或旧 `/tmp` 路径。

重要：正常模式已做语法与代码检查，但尚未现场验证冷启动。之前成功播放使用接管既有编码器模式；如果启动后没有码流，应保存以上日志，不热卸载媒体驱动。

## 5. 启动电脑服务

Ubuntu 安装依赖（如未安装）：

```sh
sudo apt update
sudo apt install python3 ffmpeg openssh-client
python3 licheerv-nano/scripts/start_pc_preview.py --board 10.225.161.1 --ffmpeg /usr/bin/ffmpeg
```

Windows PowerShell：

```powershell
python .\licheerv-nano\scripts\start_pc_preview.py --board 10.225.161.1 --ffmpeg "D:\ffmpeg\bin\ffmpeg.exe"
```

Windows 路径是示例，必须替换为实际安装路径，并保留 FFmpeg 所依赖的 DLL。如果 FFmpeg 已在 PATH，可以省略 `--ffmpeg`。发布版移除了现场专用的 Webots 路径回退。

浏览器打开 <http://127.0.0.1:8080/>。该地址指向运行接收器的电脑，不是板卡；手机不能用这个回环地址访问电脑。本版本没有开放电脑局域网页面或修改防火墙。

服务后台运行，`--foreground` 可用于前台排错。若提示端口占用，先检查已运行服务，不结束未知进程。板卡上电后，仍运行的电脑服务会重试连接；不必再启动第二个服务。

## 6. Wi-Fi 切换与停止

切换接收地址前，先停止电脑端（Ubuntu 命令；Windows 用 python）：

```sh
python3 licheerv-nano/scripts/start_pc_preview.py --stop
python3 licheerv-nano/scripts/start_pc_preview.py --board <实际Wi-Fi地址>
```

上面的尖括号是占位符，必须替换，不能原样执行。网页地址保持 `127.0.0.1:8080`。只允许一个活动视频接收器；Wi-Fi 迁移后播放尚未单独实测。

`--stop` 仅停止电脑网页和其 FFmpeg 子进程，不停止板卡编码。无人接收时板上仍排空并丢弃码流。关闭浏览器也不会停止编码。

停止板上正常模式时，先核对 `/run/h264-sender.pid` 和 ps 中的发送器身份，再向该 PID 发送 SIGTERM，由它管理编码器退出。接管模式应先向核实的编码器 PID 发 SIGINT，等编码器退出后再结束发送器。不要 killall，也不要盲用过期 PID。

媒体资源原地停启曾出现残留问题；退出不保证再次启动正常。保存日志并安排整板重启，不运行中 rmmod/insmod。

## 7. 状态与排错

浏览器或 curl 访问 <http://127.0.0.1:8080/status>：正常应 `healthy=true`、`processing_host=PC`，frames/segments 持续增加、fps 约 30。

- 电脑日志：`licheerv-nano/work/h264-pc/service.log`、`muxer.log`。
- 板卡发送器日志：`/tmp/h264-sender.log`。
- 正常模式编码器日志：`/tmp/h264-sender-encoder.log`。
- PID/启动记录：`/run/h264-sender.pid`、`/run/h264-sender.ready`；ready 不是实时健康检查。
- 页面打不开：检查电脑服务和端口占用。
- 页面无画面：检查 USB/Wi-Fi 地址、板端进程、9000 端口和编码日志。
- FFmpeg 不工作：检查实际安装路径、DLL 与 muxer.log。

旧板卡 `http://板卡IP:8080/` 不再提供本版本网页。两端均没有开机自启。TCP 9000 明文且无认证，只用于可信网络，不映射到公网。
