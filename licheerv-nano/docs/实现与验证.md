# 实现与验证记录

## 架构

板卡 GC4653 → VI/ISP → sample_venc 硬件 H.264 → FIFO → 轻量 TCP 9000 → 电脑 FFmpeg copy 封装分片 MP4 → Python 回环 HTTP 8080 → 浏览器。

`h264_sender.py` 只发送裸码流，没有 MP4 封装或网页服务。SPS/PPS 缓存用于新连接，用户态发送队列限制 256KiB，慢客户端会被关闭，无接收器时继续排空 FIFO。存在 TCP 内核缓冲，因此这不等于绝对无阻塞或严格实时。

`h264_pc_preview.py` 导入 `h264_preview.py` 的共享解析器和页面，不执行其旧板端 main。FFmpeg 子进程重连时重置 MP4 初始化状态；浏览器重建连接，不保证无缝恢复。

## 参数与时间戳

- 2560×1440 / 30fps / H.264 Constrained Baseline，无 B 帧。
- 固定 QP：I=28、P=30，码率随画面变化，不是固定上限。
- GOP 6，约 200ms 一个关键帧分片。
- 浏览器目标缓冲 300ms，超过 700ms 主动追赶，落后时跳旧分片。
- 电脑不重新编码：`-c:v copy`。

FFmpeg 7.1 接收裸 H.264 后曾产生错误播放时序，已明确添加固定 30fps 包时间戳：

```text
-r 30
-bsf:v setts=time_base=1/90000:pts=N*3000:dts=N*3000:duration=3000
-video_track_timescale 90000
```

改帧率或增加 B 帧必须重新设计，不能无条件沿用。参考：[FFmpeg setts](https://www.ffmpeg.org/ffmpeg-bitstream-filters.html#setts)。

## 已实测

2026-09-17，Windows、FFmpeg 7.1、USB 接收：

- Edge 播放 40 秒，1440p、约 30fps；注入一次 1.8 秒请求延迟后跳过旧分片继续播放。
- 主动结束本服务的电脑 FFmpeg 子进程后，接收器重连、浏览器恢复；没有停止板上编码器。
- 最后 20 秒测试累计 608 帧、报告 3 帧丢帧；没有声称零丢帧。
- 迁移前板上预览 Python 短采样约 19%–31% CPU、FFmpeg 约 6%；迁移后 3 秒差分采样发送器约 6.3%、编码器约 11.7%。
- MemAvailable 观察由约 66MiB 增至约 73MiB，不等于芯片全部可用内存，也不是严格控制的性能基准。

迁移期间接管了正在工作的编码器 FIFO，没有热重启摄像头。仅在新链路验证后结束旧板上 Python/FFmpeg，不改分辨率或帧率。迁移 PID、现场 IP 和管道路径没有固化到部署流程。
